# 1. Giới thiệu dịch vụ Worker

## 1.1. Worker là gì?

TransVidCloud tách việc xử lý video khỏi API: API chỉ nhận metadata, ký presigned URL và **đặt job vào SQS**; Worker là tiến trình **lấy job ra, transcode và ghi kết quả**. Một worker chạy trên một container Docker (image `tvc-worker`) trên EC2 trong Auto Scaling Group, không mở bất kỳ cổng inbound nào.

```text
SQS (job) --> Worker (Go + FFmpeg) --> S3 (HLS 360p/720p + thumbnail)
                    |
                    +--> DynamoDB (PROCESSING -> COMPLETED / FAILED_*)
```

## 1.2. Vị trí trong hệ thống

Worker là **thành phần duy nhất tiêu tốn CPU nặng** của hệ thống. Mọi quyết định kiến trúc quan trọng của dự án — dùng queue, dùng ASG, dùng Spot, scale theo backlog — đều xoay quanh worker:

- **Tại sao có queue?** Để upload không chờ transcode, và burst 20 video không đánh sập hệ thống.
- **Tại sao worker scale ngang?** Transcode là workload CPU-bound, đến theo đợt (burst).
- **Tại sao máy worker có thể chết?** Chạy Spot (rẻ hơn ~60-90%) để tối ưu chi phí; do đó worker phải xử lý được tín hiệu dừng và SQS phải giao lại job.

## 1.3. Phạm vi trách nhiệm

### Worker **làm** (trong scope)

1. **Consumer SQS**: long polling 20 giây, nhận message job theo schema `docs/contracts/sqs-job-message.schema.json`.
2. **Kiểm tra idempotency**: video đã `COMPLETED` thì bỏ qua và xóa message.
3. **Chuyển trạng thái**: `PENDING/FAILED_* -> PROCESSING` bằng `UpdateItem` có điều kiện.
4. **Gia hạn visibility (heartbeat)** khoảng mỗi 120 giây trong lúc job còn chạy.
5. **Tải input** từ bucket `tvc-{env}-input` về thư mục tạm.
6. **Xác thực bằng ffprobe**: thời lượng, độ phân giải, codec, có thực sự là video hay không → `FAILED_VALIDATION` nếu sai.
7. **Transcode bằng FFmpeg**: giải mã một lần, tạo HLS 360p + 720p (filter `split`, preset `veryfast`) và thumbnail.
8. **Đẩy output lên S3** đúng key và Content-Type theo `docs/contracts/s3-key-convention.md`.
9. **Ghi kết quả**: `COMPLETED` kèm `assets`, hoặc `FAILED_TRANSCODE`/`FAILED_STORAGE` kèm `errorCode`.
10. **Dọn thư mục tạm** sau mỗi job (kể cả khi lỗi).
11. **Xử lý SIGTERM**: khi EC2 Spot bị thu hồi, dừng gọn — không nhận job mới, trả job đang chạy về queue.
12. **Ghi log JSON** (có `jobId`/`videoId`) và metric cho CloudWatch — *hiện mới có log, metric chưa phát; xem [[5. Contact docs]] mục 5.6*.

### Worker **không làm** (ngoài scope)

| Việc | Ai làm |
|---|---|
| Ký presigned URL, API REST, xác thực | Phương (backend) |
| Tạo bucket/queue/bảng, lifecycle S3, Terraform | Lưu, Nguyên (cloud) |
| Dockerfile worker (image base có FFmpeg), compose | Lưu dựng, Vũ cung cấp lệnh chạy + env |
| ASG, scaling policy, metricpub | Nguyên (Vũ phối hợp về metric/log) |
| Frontend React, trình phát HLS | Vũ (thư mục `frontend/`, tài liệu riêng `docs-frontend/`) |

## 1.4. Tech stack

| Thành phần | Lựa chọn | Ghi chú |
|---|---|---|
| Ngôn ngữ | **Go** (bản ghi trong `worker/go.mod`) | Một binary tĩnh, khởi động nhanh, chiếm ít RAM — hợp máy nhỏ |
| AWS SDK | AWS SDK for Go v2 | `config`, `sqs`, `s3`, `dynamodb` |
| Transcode | **FFmpeg** + **ffprobe** | Có sẵn trong image Docker; khi dev trên máy cần cài FFmpeg |
| Chạy local | LocalStack (`AWS_ENDPOINT_URL=http://localhost:4566`) | Xem `docs/introduction/2. LOCAL_AND_CICD.md` |
| Chạy cloud | Container trên EC2 Spot, ASG min 0-1 / max cấu hình | Terraform module `compute` của Nguyên |

## 1.5. Nguyên tắc làm việc

1. **Contract là chuẩn**: worker bám 5 file trong `docs/contracts/` (SQS message, state machine, S3 key, DynamoDB, upload limits). Lệch nhau thì sửa code hoặc mở PR sửa contract — không "sửa lặng".
2. **Không tin input**: phần mở rộng file không có ý nghĩa (`quanan.webm` có thể là file text); chỉ ffprobe quyết định. Dung lượng khai báo có thể nói dối; worker tự kiểm lại.
3. **Idempotency mặc định**: key output ổn định theo `{projectId}/{videoId}` nên chạy lại chỉ ghi đè chỗ cũ; `COMPLETED` là trạng thái cuối không bao giờ bị ghi đè.
4. **Lỗi không được im lặng**: mọi nhánh lỗi phải ghi `errorCode` vào DynamoDB và log; message chỉ bị xóa khi job hoàn tất hoặc đã `COMPLETED`.
5. **Máy có thể chết bất cứ lúc nào**: thiết kế mọi bước đều coi việc bị gián đoạn giữa chừng là bình thường, không phải ngoại lệ.

## 1.6. Giới hạn đầu vào worker chịu trách nhiệm kiểm tra

Theo `docs/contracts/upload-limits.md` (lớp cuối trong chuỗi phòng thủ client → API → confirm → **worker** → lifecycle S3):

| Giới hạn | Giá trị | Biến cấu hình |
|---|---|---|
| Thời lượng tối đa | 5 phút (300 giây) | `MAX_DURATION_SECONDS` |
| Độ phân giải tối đa | chiều cao ≤ 1080 | `MAX_HEIGHT_PIXELS` |
| Định dạng | mp4, mov, mkv, webm (ffprobe quyết định) | cố định trong code |
| Dung lượng | 200 MB (API kiểm khi khai báo và khi confirm; worker tải về và có thể đối chiếu) | `MAX_UPLOAD_BYTES` |

## 1.7. Định nghĩa "worker chạy được"

Pipeline được coi là hoàn thành khi: `make up` ở local, upload một video mẫu qua API, video đi qua `PENDING -> PROCESSING -> COMPLETED` và trên S3 có đủ `master.m3u8`, 2 playlist rendition + segment, thumbnail — phát được qua `/media/...`. Đây chính là tiêu chí "Xong khi" của epic A4.
